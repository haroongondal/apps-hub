# Inflow UX rework and quieter SMS Implementation Plan

> **For agentic workers:** the owner's rule replaces superpowers:subagent-driven-development with `cd-engineering-tools:parallel-agents-coord`. Agent K (Kotlin, tasks K1 then K2, in order) and agent T (TS, task T1) run in parallel; their files are disjoint. Steps use `- [ ]`.

**Goal:** Home puts money and chats first and never hides an app, Money gets Overview / Reports / All, and promotional SMS senders fold into one "Promotions" row.

**Architecture:** Kotlin owns every query (promotional-sender rule as one SQL constant, merged app rows, Important filter, case-insensitive parties, schema v7 for the owner's override); pure Kotlin helpers hold what JVM tests can reach (generic notification title, app-row merge); `InflowCoreModule` exposes them; RN renders with `@apps-hub/ui`.

**Tech Stack:** Kotlin + SQLCipher (no JVM SQL harness, R32: SQL is proven in desktop `sqlite3` on the real schema), Expo module, React Native, `node --test`.

**Spec:** `docs/superpowers/specs/2026-11-17-inflow-ux-design.md`

## Global Constraints
- No new permission, no new dependency; `:app:processReleaseMainManifest` unchanged (expected: READ_SMS, RECEIVE_SMS, INTERNET, POST_NOTIFICATIONS, USE_BIOMETRIC, USE_FINGERPRINT, DYNAMIC_RECEIVER).
- `@apps-hub/ui` components and tokens only (`Segmented`, `Group`, `Row`, `Readout`, `Notice`, `Button`, `Sheet`); no hand-rolled colours. Copy: sentence case, active voice, no emoji, no ALL-CAPS.
- Nothing is deleted or stops being saved for promotional SMS; the rule only changes what is shown.
- Hidden OTP items (`VISIBLE_I` clause) never appear in a row or count.
- Promotional rule (spec, verbatim): a sender is promotional when more than half of its AI-read items (those with an `ai_results` row, at least 1) are kind `promotion` and none of its items is a transaction source; the owner's per-sender choice wins. It applies to SMS items only (`sms_hash IS NOT NULL` or a package in `Sms.KNOWN_APPS`).
- Schema: `SCHEMA_VERSION` 6 becomes 7; v7 is one new table, no data rewrite.

## Shared names (both agents)

Kotlin (`apps/inflow/modules/inflow-core/android/src/main/java/expo/modules/inflowcore/`):
- `core/GenericTitle.kt`: `object GenericTitle { fun isGeneric(title: String?): Boolean }` true for `^\d+ new messages?$` (any case, trimmed) and for bare `new message(s)`.
- `core/AppRows.kt`: `data class AppStat(val pkg: String, val label: String, val lastAt: Long, val today: Int, val hasChats: Boolean)`; `data class AppRow(val label: String, val pkgs: List<String>, val lastAt: Long, val today: Int, val byContact: Boolean)`; `object AppRows { fun build(stats: List<AppStat>, sms: Set<String>): List<AppRow> }` (see K1).
- SQL constants in `android/SqlItemStore.kt` (internal): `PROMO_KEYS` (a `SELECT` of promotional contact keys, no parameters), `notPromo(alias: String): String`, `GENERIC_SQL(expr: String): String`.

TS contract (agent T writes it in `modules/inflow-core/src/index.ts`; agent K implements it in `InflowCoreModule.kt`):
```ts
export interface AppRow { label: string; pkgs: string[]; lastAt: number; today: number; byContact: boolean }   // replaces the old AppRow (pkg → pkgs)
export interface HomeSummary { conversations: ConversationRow[]; inbox: AppRow[]; important: Item[]; comingUp: Todo[] }   // apps removed, inbox added
export type ItemFilter = /* existing */ | { kind: 'apps'; pkgs: string[] };
// api additions / changes
apps(startOfDay: number): AppRow[];                       // every app, newest first, same-label non-contact apps merged
contacts(pkg: string, startOfDay: number, before: number | null, beforeKey: string | null, limit: number, promo: boolean): ContactRow[];   // promo false = the main list, true = Promotions only
promotions(pkg: string): { senders: number; lastAt: number | null };   // senders folded into Promotions for this app
smsPromotion(key: string): boolean | null;                // key = conversationKey ?? senderKey of an item; null = not an SMS sender; else is it in Promotions now
setPromotion(key: string, promotional: boolean): void;    // the owner's choice
```
`home` semantics: `inbox` = apps where `byContact`, counts and `lastAt` over items of non-promotional contacts only (an app with none drops out); `important` = `importance = 'high'`, last 7 days, newest first, at most 5, not a transaction source, not from a promotional contact; `conversations` = 5 latest, promotional contacts left out, names per K2.

## Review Focus
1. A bank short-code sender (8287) with most items read as `promotion` but one a transaction source stays in the main list and on Home; with the owner's "Move to Promotions" it folds anyway, and "Keep in my list" on a promotional sender survives later AI results.
2. Contacts paging with equal `lastAt` in both lists: no row skipped or repeated, and no contact appears in both the main list and Promotions.
3. Two packages with the same label merge into one All-apps row (summed `today`, newest `lastAt`, items of both packages); a contact app never merges; an app whose only senders are promotional is absent from Inbox but present in All apps.
4. `EMAN IFTIKHAR BAF` and `Eman Iftikhar Baf` are one party (most recent spelling shown), its drill-down lists both spellings' transactions, and a party with neither label nor counterparty still opens as Unknown.
5. A notification titled `1 new message` (LinkedIn) never becomes a chat name: new captures get no conversation, old rows show the app label (not "You") in contacts and Recent chats.

### Task K2: Queries and module functions

**Files:** Modify `android/SqlItemStore.kt` (`home`, `contacts`, `list`, new `apps`, `promotions`, `smsPromotion`, `setPromotion`, constants), `android/SqlLedgerStore.kt` (`money` parties, `partyClause`), `InflowCoreModule.kt`. Proof fixtures go in `progress.md`.

**Interfaces (Consumes K1):** `AppRows.build`, `AppStat`, `GenericTitle`, `sender_promo`. **Produces:** the TS contract above.

Queries (SQL constants, each used by every query that needs it):
- `SMS_ITEM = "(i.sms_hash IS NOT NULL OR i.pkg IN (<Sms.KNOWN_APPS as quoted literals>))"`.
- `PROMO_KEYS`: one non-correlated `SELECT s.k FROM (SELECT COALESCE(i.conversation_key, i.sender_key) AS k, COUNT(r.item_id) AS ai_read, SUM(r.kind = 'promotion') AS promo, MAX(EXISTS(SELECT 1 FROM txn_sources x WHERE x.item_id = i.id)) AS has_txn FROM items i LEFT JOIN ai_results r ON r.item_id = i.id WHERE $SMS_ITEM AND COALESCE(i.conversation_key, i.sender_key) IS NOT NULL GROUP BY k) s LEFT JOIN sender_promo o ON o.sender_key = s.k WHERE COALESCE(o.promo, s.ai_read >= 1 AND s.promo * 2 > s.ai_read AND s.has_txn = 0) = 1`.
- `notPromo(a)` = `(COALESCE(a.conversation_key, a.sender_key) IS NULL OR COALESCE(a.conversation_key, a.sender_key) NOT IN ($PROMO_KEYS))`.
- Display name of a contact key `k` with newest-item columns `conversation`, `sender`, `app_label`: `COALESCE(n.name, BANK(k), usable(conversation), usable(sender without "You"), app_label, k)`; `usable(x)` = `x` unless NULL or `GENERIC_SQL(x)` (`lower(x) GLOB '[0-9]* new message' OR lower(x) GLOB '[0-9]* new messages' OR lower(x) IN ('new message', 'new messages')`); `BANK(k)` = `CASE WHEN k LIKE 'num:%' AND length(k) <= 10 THEN (SELECT NULLIF(trim(rtrim(t.account, '0123456789')), '') FROM items b JOIN txn_sources s ON s.item_id = b.id JOIN txns t ON t.id = s.txn_id WHERE b.sender_key = k ORDER BY t.at DESC, t.id DESC LIMIT 1) END` (a short code is `num:` plus at most 6 digits; the bank is the account text without its trailing digits, so `Alfalah 2310` gives `Alfalah`). The owner's rename (`n.name`) wins over the bank name.
- `stats(startOfDay, now, excludePromo)`: per-package `AppStat` rows (label `COALESCE(a.label, MAX(i.app_label))`, `hasChats` from `MAX(i.conversation_key IS NOT NULL)`), with `AND ${notPromo("i")}` when `excludePromo`, no `LIMIT`. `home().inbox` = `AppRows.build(stats(true)).filter { it.byContact }`; `apps()` = `AppRows.build(stats(false))`.
- `home().conversations`: today's query with `AND ${notPromo("i")}` on the outer item and the display name above; `home().important`: add `AND NOT EXISTS (SELECT 1 FROM txn_sources s WHERE s.item_id = i.id) AND ${notPromo("i")}`. Every item that is a transaction source is excluded, so one row per transaction holds without a second dedupe key.
- `contacts(..., promo)`: today's query with `AND ${notPromo("i")}` when `promo` is false, `AND NOT ${notPromo("i")}` when true, restricted to promotional keys only by that clause; display name above; keyset `(last, k)` unchanged. `promotions(pkg)`: `{senders, lastAt}` over the visible items of `pkg` whose key is in `PROMO_KEYS`.
- `smsPromotion(key)`: null when no item with that key matches `SMS_ITEM`, else `key IN ($PROMO_KEYS)`. `setPromotion(key, promotional)`: `INSERT ... ON CONFLICT(sender_key) DO UPDATE SET promo = excluded.promo`.
- `list` filter `"apps"`: `i.pkg IN (?, ...)` from `filter["pkgs"] as? List<*>` (empty list matches nothing).
- Parties: replace `PARTY` with `lower(COALESCE(label, counterparty, ''))` for grouping; the shown name is the spelling of the newest row (`COALESCE(label, counterparty, '')` selected as a bare column next to a single `MAX(at)`, as `contacts` already does); `partyClause` compares `lower(COALESCE(t.label, t.counterparty, '')) = lower(?)`. Note in a comment: `lower()` folds ASCII only, which covers the names seen so far.
- Module: `home` (new shape), `Function("apps") { startOfDay -> ... }` mapping `AppRow` to `{label, pkgs, lastAt, today, byContact}`, `contacts` with the extra `promo: Boolean`, `promotions`, `smsPromotion`, `setPromotion`; the old `home().apps` key is removed.
