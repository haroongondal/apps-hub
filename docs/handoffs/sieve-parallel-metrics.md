# Parallel-with-coord experiment: metrics (owner asked 2026-11-08 to monitor whether it works and what it costs, then write a skill)

Hypothesis: several implementers in ONE worktree, with coord file claims (alphabetical order, held until a pathspec commit), a folder claim around build/e2e, and messaging for dependencies, cut wall-clock without raising tokens or lowering accuracy.

## Parallel run (Tasks 1.10, 1.11, 1.12, 1.13 step 1): what to record per agent
tokens, tool uses, duration (from its notification); coord waits (which keys, how long, by `coord status` observations); refused edits; messages sent between agents; any e2e failure caused by another agent's uncommitted files; any commit that contains another agent's hunks (check `git show --stat` of each commit against the agent's own paths); deadlocks or stalled queues; fix rounds needed; controller tokens spent monitoring.

- END OF EXPERIMENT (session 4): outcome and the skill. The skill parallel-agents-coord (user skills folder, SKILL.md plus scripts/filelock) holds the protocol and the measured numbers. Summary: coord is session-scoped so it gave no exclusion between subagents (finding 1); whole-file locks on README/e2e serialised the critical path (findings 3, 5); the shared tree contaminated gates (finding 2, 4); what worked: read-only reviews and new-file outputs in parallel at no conflict cost, staggered fix wave with shared files edited last (zero lock waits), pathspec commits, per-commit review packages, a clean-export gate. Cost per task did not rise (1.10 parallel 274,698 tokens vs 1.7 sequential 261,766); total spend rose because of the extra review rounds, which found real defects (about 970k tokens for the four final reviewers). Accuracy: no loss: every task and every fix round was independently reviewed in both modes.
